# 结合 cbox-roughness 运行结果的缓存数据流说明

以下用你这次运行的真实数据（120 帧、block_size=256、23 块/帧）说明**数据在管线里怎么流动**、以及**控制台里每个数字代表什么**。

---

## 一、场景与参数

- **序列**：`video-data/teaser-scenes/cbox-roughness`，120 个 H5 文件（frame_0000.h5 ~ frame_0119.h5）。
- **每帧**：5633 个三角形，按 256 个/块划分 → **23 块**（前 22 块满 256，最后一块 256+ 余数）。
- **语义**：cbox-roughness 通常是 Cornell Box + 随时间变化的**粗糙度**，所以几何大致不变，只有少量三角形（某块内）的材质在变，导致**每帧约 22 块命中、1 块未命中**。

---

## 二、单帧内的数据流（以某一帧为例）

```
frame_0050.h5 (5633 tris)
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│ 1. 块划分                                                         │
│    block_size=256 → 23 个块                                       │
│    块0: tri [0:256],  块1: [256:512],  ...  块22: [5376:5633]    │
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│ 2. 逐块：哈希 → 查缓存 → 命中则复用 / 未命中则编码并写入            │
│                                                                   │
│    块0  key=hash(几何+材质) → cache.get(key) → 命中 → 直接用缓存   │
│    块1  → 命中                                                   │
│    ...                                                            │
│    块21 → 命中                                                    │
│    块22 → 未命中 → construct_seq(块22) → cache.put(key, tri_emb)  │
│                                                                   │
│    本帧结果：hit=22, miss=1  →  frame_hit% = 22/23 ≈ 95.7%       │
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│ 3. 重组整场景序列                                                 │
│    tri_emb_full = [块0的768维, 块1的..., ..., 块22的...]          │
│    seq_full = [reg_tokens(16) | tri_emb_full(5633)]  → [1,5649,768]│
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│ 4. 视图无关层（12 层 Transformer）                                 │
│    对 seq_full 做全局 attention，得到带全局光照的序列              │
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│ 5. 视图相关层 + 后处理                                            │
│    输出 [1, 1, 512, 512, 3]（1 视角），min/max 如日志所示          │
└───────────────────────────────────────────────────────────────────┘
```

所以你看到的 **blocks=23, hit=22, miss=1, frame_hit%=95.7** 表示：这一帧 23 次块查询里，22 次命中缓存、1 次未命中并新写进缓存。

---

## 三、跨帧的缓存如何累积（和你这次打印的对应关系）

- **第 0 帧（frame_0000.h5）**  
  - 缓存为空，23 块全部未命中 → **hit=0, miss=23**。  
  - 23 个块的编码都算一遍并写入缓存 → **cache_size=23, memory_mb=22.0**。

- **第 1 帧（frame_0001.h5）**  
  - 粗糙度等有轻微变化，多数块几何+材质与第 0 帧相同。  
  - 23 次查询：22 次命中（和上一帧相同的块）、1 次未命中（变化发生在那块里）→ **hit=22, miss=1, frame_hit%=95.7**。  
  - 只新写入 1 个块 → **cache_size=24, memory_mb=23.0**。

- **第 2～119 帧**  
  - 每帧仍是 23 块查询，**几乎总是 22 hit + 1 miss**（变化集中在某一块，例如粗糙度动画只影响部分三角形）。  
  - 每帧多 1 个新 key 被写入 → 缓存每帧 +1 条：  
    - 帧 2：size=25  
    - 帧 50：size=52  
    - 帧 119：**size=142, memory_mb=141.0**。

因此：

- **“每帧 1 个 miss”** = 每帧有且仅有 1 个块的内容（几何或材质）和之前出现过的块都不同，需要重新编码并加入缓存。  
- **“cache_size 从 23 涨到 142”** = 120 帧里一共出现了 142 种不同的块（23 + 119 个新块），对应 142 条 key→value。

## 四、你看到的打印数字分别代表什么

| 打印项 | 含义（结合本次运行） |
|--------|----------------------|
| **tri=5633** | 本帧三角形总数，每帧相同。 |
| **blocks=23** | 本帧被拆成 23 块（5633÷256 向上取整）。 |
| **hit / miss** | 本帧 23 次块查询中，命中的次数和未命中的次数。 |
| **frame_hit%=95.7** | 本帧命中率 = hit/(hit+miss)，22/23≈95.7%。 |
| **cache_size** | 当前缓存里**不同块**的个数（不同 key 的个数）。 |
| **memory_mb** | 当前缓存占用的内存（约 1MB/条，142 条≈141 MB）。 |
| **output shape** | 渲染结果张量 [1, 1, 512, 512, 3]（batch=1, 1 视角, 分辨率 512×512, RGB）。 |
| **min/max** | 该帧 HDR 像素值范围，随粗糙度/光照略有变化（如 0～1.56、0～1.59）。 |

## 五、结尾汇总数字的含义

```
总帧数           120
总查询次数       2760  = 120 帧 × 23 块/帧
总命中           2618  = 绝大部分查询命中
总未命中         142   = 120 帧里新出现的“新块”总数（23 + 119）
整体命中率       94.86% = 2618 / 2760
缓存条目数       142   = 全序列中出现的不同块种类数
缓存占用         141 MB
```

- **总未命中 142**：第 0 帧 23 个 + 之后 119 帧每帧 1 个 = 142 个“新块”被编码并写入缓存。  
- **整体命中率 94.86%**：2760 次块查询中有 94.86% 直接用了缓存，只有 5.14% 走了编码器。  
- **首帧全 miss、末帧 22 hit 1 miss**：和上面“首帧填满 23 块，之后每帧只变 1 块”的语义一致。

## 六、数据流小结（对应到代码和日志）

1. **输入**：每帧一个 H5（triangles, texture, vn, c2w, fov 等）。  
2. **块划分**：5633 tri → 23 块，每块 256（最后一块略少）。  
3. **块级缓存**：每块用 (tri_vpos, texture, vn) 算 **block_key**，查 **BlockCache**；  
   - 命中 → 直接用缓存的 `tri_emb`；  
   - 未命中 → `construct_seq` 算该块编码并 **put** 进缓存。  
4. **重组**：23 个块的 tri_emb 拼成整场景序列，再接 **transformer + view_transformer** 得到图像。  
5. **打印**：每帧的 hit/miss/cache_size/memory_mb 就是上述 2～4 步的统计；  
   结尾的**缓存命中汇总**是 120 帧累计的总查询数、总命中/未命中、整体命中率和最终缓存大小。

这样，你看到的每一行日志和最后的汇总，都对应到“按块查缓存 → 命中复用 / 未命中编码并写入 → 重组后做全局与视角相关渲染”的完整数据流。
